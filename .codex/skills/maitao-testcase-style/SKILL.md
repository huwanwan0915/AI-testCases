# 麦淘内部测试用例风格指南（XMind优先）

## 使用时机
- 当用户要求“按照我的风格”“按照麦淘旅行家用例风格”“按脑图/XMind风格”编写或更新测试用例时。
- 当需求文档来自 `requirments/+麦淘旅行家测试用例（落地页）.md`、同风格脑图导出稿，或仓库内已有同风格 testcase 文件时。
- 当 `requirements-testcase-writer` 已负责通用“从需求生成用例”的流程，而当前任务还需要继续沿用麦淘既有措辞、颗粒度、模块顺序和 XMind 分支节奏时。
- 当用户未额外指定格式，但任务是在本仓库中生成/补充内部测试用例时，也默认按本技能的风格执行。
- 当需要对齐仓库内既有风格样例时，优先参考 `testcases/+麦淘旅行家测试用例（落地页）.xmind`，必要时辅看 `testcases/+麦淘旅行家测试用例（落地页）.md`。
- 若用户只需标准表格或西式模板，请勿启用本技能。

## 默认交付格式
1. 默认最终交付物是 `testcases/` 下的真实 `.xmind` 文件，不是表格，也不是普通 Markdown。
2. 除非用户明确要求查看或保留 Markdown 草稿，否则不要在 `testcases/` 创建、更新、同步任何 `.md` 测试用例文件；中间结构稿、原型落位草稿默认放临时目录。
3. XMind 默认结构为：`根节点 -> +页面/模块节点 -> +功能节点 -> 用例节点 -> 步骤内容节点 -> 预期结果内容节点`。
4. 默认不要额外创建名为 `测试步骤` 或 `预期结果` 的中间节点，直接把编号文本写入对应内容节点。
5. 画布默认沿用仓库既有风格：`逻辑图`、`晨曦`、`彩虹分支开启`、`同级主题对齐开启`。

## 写作流程
1. **收集信息**：优先打开 `testcases/+麦淘旅行家测试用例（落地页）.xmind` 对齐节点层级和颗粒度；需要检索具体文案时，再用 `rg "模块名" testcases/+麦淘旅行家测试用例（落地页）.md` 定位对应内容；必要时同步查阅其它需求文件。
2. **先对原型落位**：如果需求包含原型图、Axure 导出页、页面截图、HTML 原型页，必须先按页面从上到下拆出真实页面区域，再把每条文字描述挂到对应区域下面；未完成“原型区域 -> 文字规则 -> 用例节点”一一对应前，不要先写 case。若需中间草稿，默认放临时目录，不留在 `testcases/`。
3. **回查历史知识库/关联需求**：拆完当前需求后，默认主动回查知识库和历史同类需求，判断是否存在可复用的旧规则、旧分支、旧埋点拆法；不要只盯当前文档单独写。
4. **划分模块**：先按页面元素和页面区域搭骨架，再按页面从上到下顺序列出模块与子节点，确认是否需要新增二级或三级标题。
5. **确定交付形态**：默认直接按 XMind 节点组织并产出 `.xmind` 文件，不再同步 Markdown 版本。
6. **确定 case 粒度**：默认先尝试“一个页面模块写成一个完整 case”；只有当模块内部场景明显独立、且拆开更清楚时，才拆成多个 sibling case。
7. **挂载规则**：把需求描述里的展示规则、交互规则、状态规则、异常规则，放到它实际发生的页面元素下面，不单独抽成脱离页面的规则模块。
8. **先拆排列组合**：遇到需求文档中的条件判断、展示分支、价格类型、人数类型、按钮状态、字段显隐、库存状态、权限状态、时间状态等规则，先把“影响结果的维度”全部列出，再做排列组合，筛出业务上有意义的全量分支。
9. **展开步骤**：写清楚入口、前置条件、操作路径，必要时拆分不同端或账号态；若一个 case 覆盖多个分支，步骤中要写明需准备哪些组合数据。
10. **描述预期**：先写页面元素，再写默认展示，再写切换交互，再写异常/边界；对排列组合后的多分支情况，顶层提示语句仍保留 `1.` `2.` `3.` 这类顺序编号，若该条下面有真正分支，再在下一层直接接 `a.` `b.` `c.` `d.` 分项罗列；若某个字母分支下还要继续补充非分支描述子项，则写成 `d-1）`、`d-2）`、`c-3-a）` 这类形式。不得写成 `1.a.`、`1-2a.`、`2.d-1.` 这类混合编号，也不得只写“按规则显示”。
11. **主动补交互**：如果页面里有 Tab、品类标签、线路/套餐、筛选、展开收起、关闭重开、登录跳转、底部栏联动，默认都要考虑是否写进同一个 case。
12. **串联编号**：客户端用例编号沿用 `PK-C-xxx`，埋点 `PK-A-xxx`，后台 `PK-B-xxx`，放在 `###` 标题或预期首条。
13. **互锁校验**：逐条比对原需求，确保没有漏掉模块/子条件；如需求含“见用例《xxx》”需补充跳转链接或引用说明。

## 原型对齐强制规则
- 只要需求包含原型图、页面截图、Axure 导出 HTML、交互稿、标注图，就必须先做“原型落位”，再写用例。
- 需要落地执行时，优先打开 `references/prototype-alignment-template.md`，先按模板完成原型区域拆分和文字挂载，再写正式 case。
- 需要先快速起一份“原型落位草稿”时，可运行；若未显式传 `--output`，草稿默认写到系统临时目录：

```bash
node .codex/skills/maitao-testcase-style/scripts/generate_prototype_alignment_draft.js --page "产品详情页" --section "价格横幅" --section "价格说明弹层"
```

- 如果已有 Axure/HTML 原型页，想先自动起一版“页面区域骨架 + 候选补充”，再人工整理，可运行；若未显式传 `--output`，草稿默认写到系统临时目录：

```bash
node .codex/skills/maitao-testcase-style/scripts/html_to_prototype_alignment_draft.js --input "requirments/日历改造/产品详情.html"
```

- `html_to_prototype_alignment_draft.js` 的定位是“自动初始化草稿”，不是自动产出最终落位结果：
  - 它会先按页面类型给一版更稳定的默认区域骨架，例如 `价格信息区`、`价格说明弹层`、`团期卡片`、`底部按钮`
  - 再从 HTML 原型中的短文本里补充候选区域
  - 最后仍必须人工删除噪音项、合并重复项，并把文字规则逐条挂到保留区域下
- 若自动稿里出现按钮文案、价格值、状态文案、活动标签等文本，不要直接当作正式区域名；优先回到原型图，把它归并到真正的页面区块，例如 `价格信息区`、`咨询入口`、`团期卡片`。

- 原型落位的最小要求：
  - 先按页面从上到下列出所有可见区域，例如 `价格横幅`、`起售价`、`价格说明弹层`、`团期卡片`、`底部按钮`、`咨询入口`
  - 再把文字需求逐条挂到这些区域下面
  - 若一条文字规则影响多个区域，要拆开分别挂载，不要写成一个抽象规则模块
- 如果一个规则在原型图上找不到明确落点，先标记为 `待确认`，不要先凭抽象理解写成 case。
- 页面区域命名优先使用原型图/页面上能直接看到的名称，不优先使用需求文档里的抽象章节名。
- 写 case 前先问自己：
  - 这个 case 挂在原型图上的哪个区域？
  - 这个步骤是在页面上点哪里/看哪里？
  - 这个预期是在页面上哪个位置看到？
  - 如果回答不了，说明还没完成原型对齐，不应继续写。
- 默认禁止先按“起价逻辑”“库存逻辑”“展示规则”“按钮规则”这类抽象逻辑名分组；必须先落到真实页面区域。
- 原型图驱动的优先级高于文字摘要驱动；同一需求冲突时，先检查是否是自己没把文字挂到正确原型区域，而不是先改写 case。
- 如果自动抽取结果和原型图视觉分区冲突，以原型图视觉分区为准，不以抽取到的文案词为准。

## 日历改造风格补充
- 遇到“详情页 -> 日历弹窗 -> 全部日历弹窗 -> 资源页”这类连续链路时，先按用户实际浏览/操作路径拆主模块，不要先按抽象规则点拆树。
- 若需求同时包含 UI 校验和埋点校验，默认拆成两棵一级树：`+前端`、`+神策埋点`；不要把埋点 case 混写在前端展示 case 下面。
- 前端模块优先贴近真实页面或弹层命名，例如 `+产品详情`、`+日历弹窗`、`+全部日历弹窗`、`+选择资源页`；埋点模块优先按“页面-事件名”命名，例如 `+活动详情页-ProductDetailClick`。
- case 标题优先使用两类模板：
  - `动作 + 页面区域/对象（条件A&条件B&条件C）`
  - `模块/弹窗 - 校验点（场景A/场景B）`
- 步骤默认保持短链路写法，通常 2~4 步，重点写清入口、前置数据、操作路径；复杂信息尽量收在预期中，不把步骤写成需求复述。
- 预期默认遵循“先元素、再默认态、再切换交互、再条件分支”的顺序，且分支必须写成可观察结果，不写“按规则展示”这类抽象话。
- 对高状态复杂度模块，优先收成大 case，在同一个预期节点下展开多分支；尤其适用于团期卡片、价格横幅、出行人数、底部按钮、说明弹层。
- 日历类需求默认优先检查这些维度是否已拆开：品类、是否多线路、售卖方式、团期状态、调价/优惠类型、库存状态、截止时间、登录状态、专员/咨询群配置、会员态。
- 当多个 case 共享公共逻辑时，允许在预期中写 `见用例《xxx》` 做引用，避免把同一段价格、卡片、弹层规则全文重复拷贝；但最终要补齐被引用用例名。
- 对咨询链路、登录跳转、专员/进群分支、房差/车差说明、价格明细、候补入口这类转化敏感节点，默认单独落 case，不要只作为一句补充文案带过。

## 原稿对齐与返工
- 用户更在意“原型图真实区域和需求文字是否一一对应后再落 case”，而不只是“规则有没有写到”。
- 当用户同时给了需求文档和自己写的原稿/XMind，优先级固定为：原型图真实区域 > 用户原稿的模块命名/收拆方式/编号节奏 > 需求文字规则。
- 拆完当前需求后，默认再回查知识库和历史关联需求，判断哪些规则属于历史沿用、哪些是本次新增，不要把当前需求当成孤立需求处理。
- 若用户反馈“你写的和我写的差很多”，默认不要整份重写，按顺序返工：先校正模块骨架，再补漏分支，再把总结句改成页面结果，再调整 case 收拆，最后统一文风。
- 默认每一轮返工只改一类问题，不同时大改结构、大改文风、大改编号。
- 若用户原稿已经把某一块写成一个大 case，默认先保留大 case，再在预期下补分支；若用户原稿把埋点拆成“一条事件一个 case”，不要再合并。

## 标题与文风细则
- case 标题默认写成“查看/点击/切换 + 页面区域”，少用“模块名 + 逻辑名”。
- 预期里优先使用 `显示如下：`、`情况如下：`、`点击后如下：`、`切换后如下：`。
- 避免使用 `按规则显示`、`正常展示`、`符合需求`、`逻辑正确` 这类总结句。
- 分支句子要直接落到最终页面展示，不要停在“取最低价场次显示该场次价格”这种半截句。
- 同一模块下编号节奏尽量统一：普通顺序内容可用 `1. 2. 3.`；顶层编号下的真正分支用 `a. b. c.`；若分支下继续补充说明型子项，用 `d-1）`、`d-2）`、`c-3-a）` 这类写法；不要写成 `1.a.`、`1-2a.`、`2.d-1.`。只有需要强贴用户原稿且用户原稿本身就是该格式时，才保留 `1） 2）` 这类纯顺序子项。

## 埋点 case 细则
- 纯埋点 case 默认贴用户原稿写法：步骤只写入口和点击动作，预期直接写 `记神策事件 XXX，button_name：YYY`。
- 如果用户原稿把埋点拆成“一条 button_name 一个 case”，不要再合并成“多个按钮共一个 case”。
- 埋点标题优先贴用户原稿语义，如 `查看价格说明`、`更多日期咨询专员`；`查看价格说明`、`计算我的出行价格`、`查看全部日期`、`房差说明`、`车差说明`、`价格明细`、`咨询专员`、`进群咨询`、`候补添加专员`、`候补进群咨询` 默认单独落 case。

## 日历类最小模板
- 当需求主体是“团期/日历/价格说明/选择资源/咨询入口”时，可优先按下列骨架起脑图，再按实际需求删减：

```text
+项目测试用例
  +前端
    +产品详情
      +价格横幅/价格信息
      +起售价&价格说明弹层
      +选择团期入口
    +日历弹窗
      +弹窗UI
      +团期卡片
      +出行人数/份数/房间数/车型数
      +房差说明/车差说明
      +已选浮条&底部按钮
    +全部日历弹窗
      +进入全部日历弹窗
      +全部日期列表
      +咨询入口
    +选择资源页
      +页面UI与咨询入口
  +神策埋点
    +活动详情页-ProductDetailClick
    +填写订单页-SelectDateClick
```

- 如果业务没有资源页、没有埋点、没有多线路、没有房差/车差，就直接裁掉对应模块，不要为了套模板硬保留空节点。
- 如果同一个页面同时存在“多人售卖/份数售卖/卡预约/多线路/非多线路”，优先按“展示结构是否变化”决定是否拆 case，而不是机械按字段名拆。
- 如果只有一个入口但内部状态很多，优先写成：

```text
+模块节点
  +功能节点
    查看XX（条件A&条件B&条件C）
      1.前置条件...
      2.执行操作...
        1.显示元素A/B/C
        2.默认态如下：
        a....
        b....
        3.切换/点击后如下：
        a....
        b....
        4.异常/边界如下：
        a....
        b....
```

- 如果是纯埋点 case，优先写成“操作路径 + 事件结果”两层，不补多余 UI 细节，避免和前端 case 重复。
- 需要直接复制骨架时，优先打开 `references/calendar-xmind-skeleton-template.md`。
- 需要快速生成一个可裁剪骨架时，可运行：

```bash

```

- 需要直接生成真实 `.xmind` 文件时，可运行：

```bash

```

- 如果已经先写好了 Markdown 结构稿，再转成真实 `.xmind`，可运行；默认建议结构稿放临时目录，`testcases/` 只保留最终 `.xmind`：


- 如果需要把现有 `.xmind` 反向导出成 Markdown 结构稿，可运行；默认建议导出到临时目录，除非用户明确要求保留：


## 日历类默认检查项
- 是否覆盖 `多线路/非多线路` 两类展示结构差异。
- 是否覆盖 `预定人数/预定份数/卡预约` 等售卖类型差异。
- 是否覆盖 `售卖中/即将售罄/已成团/未成团/可候补/已售罄/已满额/已截止` 等团期状态差异。
- 是否覆盖 `调价/立减/会员/拼单/非优惠` 等价格展示差异。
- 是否覆盖 `库存>=阈值`、`库存<阈值`、`不限量`、`限量`、`不可售` 等库存或售卖边界。
- 是否覆盖 `登录/未登录`、`已配置专员/未配置专员`、`已配置咨询群/未配置咨询群` 的入口差异。
- 是否覆盖 `月份切换`、`套餐切换`、`线路切换`、`关闭重开` 后的默认选中态与保留态。
- 是否覆盖 `价格说明`、`房差说明`、`车差说明`、`价格明细` 等说明型弹层或弹窗入口。
- 是否补齐 `见用例《xxx》` 的引用目标，避免留空。

## 文本风格
- 中文标点优先，保持“，”“：”“（）”等写法。
- 数字或字母编号需遵循当前风格规则：顶层顺序项用 `1.` `2.` `3.`，真正分支用 `a.` `b.` `c.`，分支下的描述型子项用 `d-1）`、`c-3-a）`；不要写成 `1.a.`、`1-2a.`、`2.d-1.` 这类混合编号。
- 语气保持客观陈述，例如“显示”“提示”“进入”。
- 涉及金额、时间、链接，要抄原文，不自行推测。
- 涉及仓库通用业务口径，例如 `预订产品价格设置`、起价匹配、日期价格展示等，沿用 `requirements-testcase-writer` 中定义的默认业务解释；本技能不重复定义业务规则。
- 默认不要先按抽象功能点或规则点分组；优先写成“页面区域/元素 -> 场景”。
- 模块命名贴近页面真实元素，例如 `头图`、`悬浮按钮`、`弹窗`、`列表`、`卡片`、`底部栏`，避免泛化命名如 `规则校验`、`功能模块`、`列表逻辑`。
- 如果用户偏好“大 case”，优先把一个模块内的显示逻辑、切换交互、边界情况收敛到同一个 `###` 用例标题下，再在预期里用 `a.` `b.` `c.` `d.` 展开。
- 若一个预期节点已经使用 `a.` `b.` `c.` `d.` 枚举分支，则应写成 `1. 默认态如下：` 下一层接 `a...`、`b...`；不要写成 `1.a...`、`1-2a...` 这种混合编号。
- 若某个字母分支下还需继续补充非分支描述项，则写成 `d-1）...`、`d-2）...`、`c-3-a）...`，不要再在前面补顶层数字，也不要把它误写成新的 `a.` `b.` `c.` 分支。
- 对标签、角标、按钮状态、字段显隐这类多条件逻辑，不要只写一句“按规则显示”，要把关键组合列出来。
- 写卡片、弹窗、表格、底部栏时，默认先检查是否遗漏页面元素描写，例如头图、标题、标签、评分、价格、按钮、关闭按钮、已选态、空态按钮。
- 对日历/团期类模块，默认优先把状态文案直接写全，例如 `报名中`、`仅余N人/份/车/房间`、`余位通知`、`已满员`、`确定成行`、`距开售还剩 D天hh:mm:ss`，不要只保留状态名称。

## 常见反例
- 反例 1：一个弹窗模块被拆成十几个很碎的 case，每个 case 只写一句结论。
  正确方向：先收成 1~3 个大 case，再在预期里拆 `a.` `b.` `c.` `d.`。
- 反例 2：只写“列表按规则展示”“标签按规则显示”，没有写列表里到底有什么元素、标签在什么条件下显示或不显示。
  正确方向：先写页面元素，再列条件组合。
- 反例 3：只写默认态，不写切换 Tab、切换标签、切换线路/套餐后的变化。
  正确方向：把切换前后差异写进同一个 case。
- 反例 4：模块名写成 `规则校验`、`功能汇总`，看不出这是页面上的哪个区域。
  正确方向：改成真实页面元素名，如 `选择活动弹窗`、`产品卡片`、`底部栏`。
- 反例 5：把需求原文直接拆行塞进预期，没有转成可观察的结果。
  正确方向：改成“显示什么、点击后怎样、切换后怎样、异常时提示什么”。
- 反例 6：需求里明明有多个条件维度，但只写了 1~2 条示例，没有把所有有业务意义的排列组合列全。
  正确方向：先拆维度，再穷举关键组合，至少覆盖正常、缺失、并存、兜底、互斥、空态。
- 反例 7：先按“起价逻辑”“库存逻辑”“入口逻辑”分组，再把页面元素混塞进去。
  正确方向：先按原型图上的真实区域分组，例如 `价格横幅`、`价格说明弹层`、`团期卡片`、`底部按钮`，再把对应规则挂进去。
- 反例 8：文字规则理解对了，但没有对应到原型图上的具体位置，导致用例标题和模块名都很抽象。
  正确方向：先完成“原型区域 -> 文字规则 -> 用例节点”一一对应，再写标题和预期。

## 收拆判断
- 优先收成一个大 case：
  - 同一模块里的元素、默认态、切换态、边界态彼此强关联
  - 用户偏好旧脑图那种“大 case + 多分支预期”
  - 拆开后会造成重复步骤和重复前置条件
- 优先拆成多个 case：
  - 同一模块内存在几个明显独立的交互目标
  - 某个分支需要完全不同的入口、数据准备或预期结构
  - 用户明确要求更细颗粒度
- 默认先收后拆，不要先碎写再尝试合并。

## 质量检查清单
- [ ] 若用户未明确要求其它格式，最终交付优先为 `.xmind`。
- [ ] 未额外生成或同步 `.md` 测试用例文件。
- [ ] XMind 节点结构符合“页面/模块 -> 功能 -> 用例 -> 步骤 -> 预期”的层次，不回退成表格思路。
- [ ] 每个模块至少有一个 `###` 节点。
- [ ] 模块顺序符合页面从上到下的阅读/操作顺序。
- [ ] 若有原型图/原型页，已先完成“原型区域 -> 文字规则 -> 用例节点”对齐。
- [ ] 用例先挂在页面元素下，再展开正常、异常、边界场景。
- [ ] 每个重点模块都检查过是否更适合写成“一个完整 case + 多分支预期”。
- [ ] 预期结果里先有页面元素描写，再有交互变化和条件分支。
- [ ] Tab切换、标签切换、线路/套餐切换、展开收起、关闭重开等交互没有遗漏。
- [ ] 需求里涉及的条件维度已先拆解，再按业务意义做过排列组合。
- [ ] 标签/角标/显隐逻辑已用 `a.` `b.` `c.` `d.` 列出关键组合。
- [ ] 已覆盖“同时存在/仅一种存在/目标值缺失/组合并存/兜底命中/全部缺失”等关键分支，不只写示例分支。
- [ ] 步骤和预期都写全，且步骤与预期数量、顺序匹配。
- [ ] 涵盖正常、异常、空态、埋点/后台等多维视角。
