# 线路PK返工经验沉淀

本文件基于 `线路PK` 测试用例重写过程中的多轮返工整理，适用于：
- 用户已提供自己既有的 XMind 风格
- 需求同时包含前端、埋点、后台
- 用户对模块归属、case 收拆、编号节奏、最终 XMind 入库层级非常敏感

## 先看什么
- 先看用户现有 XMind 的模块顺序和模块归属，不要一上来按自己理解重组
- 先看原型/页面真实区域，再决定哪些内容挂在同一模块
- 先确认最终文件是否要上传 Coding；若要上传，最终成品层级必须优先满足 Coding 识别

## 返工优先级
当用户反馈“写得不对”时，按这个顺序返工：

1. 先改模块骨架
2. 再改模块归属
3. 再改 case 收拆
4. 再改编号节奏
5. 最后才改文案表述

不要一轮里同时大改结构、编号、文案，容易越改越乱。

## 模块归属判断

### 1. 先按页面真实区域，不按抽象逻辑
- 正确：`+PK结果页 / +PK结论`
- 正确：`+PK结果页 / +PK详情-默认`
- 错误：`+PK结果页 / +PK结论与PK详情-默认`

- 正确：`+分享结果页 / +分享`
- 正确：`+分享结果页 / +分享结果页基础展示`
- 错误：`+分享结果页 / +分享与分享结果页基础展示`

### 2. 一个模块名里不要混挂多个独立区域
出现以下信号时，默认要拆模块：
- 一个模块名里出现“与”“、”连接了两个页面区域
- 一个模块名同时包含“页面入口 + 弹窗”“分享 + 结果页”“按钮区 + 反馈弹窗 + 咨询弹窗”
- 用户已经明确指出“这个应该挂到另一个层级下面”

### 3. 卡片内元素默认挂回卡片
如果某项内容本质上是卡片组成元素，优先挂在卡片模块下，不单独漂成并列模块。

典型例子：
- `产品卡片套餐` 属于 `产品卡片`
- 线路/套餐/标签/评分/销量/选中态 默认都先看是否属于卡片展示元素

## 大 case 与拆 case 判断

### 应该收成大 case
- 同一个页面区域下，元素、默认态、切换态、边界态彼此强关联
- 拆开后只会重复步骤和前置条件
- 用户原稿本来就是按该区域收成一个大 case

### 应该拆开写
- 展示条件、点击交互、按钮动效本来就是几个独立验证目标
- 弹窗基础展示、登录态返回、Tab 默认态、卡片元素、选择限制彼此能独立失败
- 一个区域里有多个不同触发目标，例如 `分享`、`反馈弹窗`、`咨询客服`

### 强规则
- 不要强行写大用例
- “都属于同一功能” 不等于 “应该写成同一个 case”
- 是否拆开，优先看是不是同一个页面区域驱动、是不是同一个触发目标驱动

## 编号节奏
- 顶层顺序内容：`1.` `2.` `3.`
- 真正分支：`a.` `b.` `c.` `d.`
- 分支下的说明型子项：`d-1）` `d-2）` `c-3-a）`
- 本段虽然来自 `线路PK` 返工总结，但规则本身适用于本仓库所有测试用例，不只适用于 `线路PK`。

### 分支判定口诀
- 看是不是“条件不同 -> 结果不同”，是就拆 `a. b. c.`
- 看是不是“固定元素清单 / 固定展示清单 / 固定交互清单 / 固定输入清单”，是就写 `1） 2） 3）`
- 若同一条里并列列了多个条件对象，例如“团购/卡预约/隐藏/不可售”“有数据/无数据”“单线路/多线路”“有评价/无评价”“未完成/已完成”，即使它们句式接近，也按分支处理，不要压成一个纯顺序句子
- 若某个字母分支下面还要继续补固定说明，用 `b-1）`、`b-2）`，不要新起并列 `a. b. c.`

不要写成：
- `1.a.`
- `1-2a.`
- `2.d-1.`

## 结构稿与成品的存放
- 若用户只要最终一个 XMind，结构稿、返工稿、反导稿一律放 `/tmp`
- `testcases/` 只放最终 `.xmind`
- 不要把每轮返工生成的结构稿堆在 `testcases/`

## Coding 入库结构
如果最终 XMind 要上传 Coding，用例层级必须是：

```text
用例名称
  测试步骤
    预期结果
```

注意：
- 不要插入独立的 `测试步骤` 标签节点
- 不要插入独立的 `预期结果` 标签节点
- `预期结果` 必须是叶子节点
- `1）2）3）`、`a. b. c.`、`b-1）` 这类内容都直接写在同一个结果节点正文里
- 不要把预期结果拆成多层额外说明节点，否则容易影响识别

## 今日新增经验

### 1. 语义可以有多个一级结果块，XMind 入库层级不能继续外扩
- 文案层面可以保留：
  - `1. 品类标签如下`
  - `2. 当前品类状态如下`
  - `3. 提交校验如下`
- 但如果最终成品要上传 Coding，这些一级结果块只能作为同一个 `预期结果` 节点正文里的多段文本存在，不能在 `预期结果` 后再继续展开新的 XMind 子节点

### 2. 不要把“固定描述”和“状态分支”混在同一层编号
- 正确写法：
  - `1. 页面元素如下：`
  - `1）...`
  - `2）...`
  - `2. 状态如下：`
  - `a. ...`
  - `b. ...`
- 错误写法：
  - 前两条是固定描述，第三条突然开始条件差异，但仍继续写 `3）4）`

### 3. 导出正确不等于视觉正确
- 不能只看 Markdown 结构稿对不对
- 不能只看脚本是否成功生成 `.xmind`
- 还要反查最终 XMind 是否满足用户要的视觉层级：
  - 是否只保留到 `用例名称 -> 测试步骤 -> 预期结果`
  - `预期结果` 后是否错误展开了新的结果节点
  - 分支与固定描述是否在同一节点正文中按正确编号呈现

### 4. 返工时先确认用户这轮纠正的是“文案语义”还是“XMind层级”
- 若用户说“这个应该改成分支结构”，优先改文案编号语义
- 若用户说“测试结果后面不需要再有新的节点”，优先改导出层级，不要再去改文案内容
- 若两者都不对，先修层级，再修文案编号

## 生成后的自检
生成完成后，至少检查：
- 模块是否还存在“混挂两个区域”的标题
- 卡片元素是否漂成了错误的并列模块
- 是否为了追求完整把几个独立目标硬并成大 case
- 最终 XMind 是否仍是 `用例名称 -> 测试步骤 -> 预期结果`
- `预期结果` 是否仍为叶子节点，而不是又展开出新层级
- 固定描述是否用了 `1）2）3）`，分支结果是否用了 `a. b. c.`
- 某条里并列列出的多个条件对象，是否已拆成分支，而不是压在一个纯顺序句子里
- 临时稿是否误写进 `testcases/`

## 这类需求的推荐拆树

```text
+前端
  +产品详情
  +我的足迹
  +我的收藏
  +选择活动弹窗
  +PK结果页
  +分享结果页
+神策埋点
  +ProductDetailClick
  +LinePKStart
  +LinePKClick
+后台
  +线路PK记录
  +线路PK记录详情
```

在 `PK结果页` 下继续优先按真实区域拆：
- `+思考过程与结果输出`
- `+PK结论`
- `+PK详情-默认`
- `+PK详情-看不同`
- `+筛选维度`
- `+底部功能按钮`
- `+使用反馈弹窗`
- `+更多维度对比弹窗`
- `+咨询客服`

## 常见误区
- 误区 1：看到内容相关，就并到一个模块标题里
  - 正确做法：先看是不是同一个页面区域
- 误区 2：看到都是一个功能链路，就强行写成一个大 case
  - 正确做法：先看是否是独立触发目标
- 误区 3：用户指出层级错了，还先去改文案
  - 正确做法：先改模块归属
- 误区 4：中间结构稿也放到 `testcases/`
  - 正确做法：中间稿默认放 `/tmp`
- 误区 5：只校验 Markdown 结构稿，不校验最终 XMind
  - 正确做法：最终成品也要再校验一次
