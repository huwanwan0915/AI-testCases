# 日历改造需求理解知识库

本文件沉淀本次“日历改造”需求在理解和写用例时形成的稳定知识点。  
用途不是替代正式需求文档，而是让后续处理同类需求时，先带着正确的理解框架去读原型和文字描述。

## 一、先记住这次最重要的教训

- 最大问题不是“少写了几条 case”，而是没有先把原型图和文字描述一一对应。
- 一旦没先做这步，后面很容易出现：
  - 模块树写成抽象逻辑树，而不是页面区域树。
  - 标题写成 `逻辑/规则/功能汇总`，而不是 `查看/点击 + 页面区域`。
  - 预期写成“按规则显示”，而不是页面上能直接看到的结果。
  - 用户原稿是“大 case + 多分支预期”，自己却拆成很多碎 case。

## 二、这类需求的正确理解顺序

处理“产品详情 -> 日历弹窗 -> 全部日历弹窗 -> 资源页 -> 埋点”链路时，默认按这个顺序理解：

1. 先看原型图。
2. 先拆真实页面区域。
3. 再把文字需求逐条挂到页面区域下。
4. 再识别哪些地方存在条件组合。
5. 最后才写 case。

不要反过来，不要先看见“起价逻辑/库存逻辑/规则说明”几个字就开始写抽象规则树。

## 三、原型图优先于抽象章节名

这类需求里，真正稳定的不是文档章节名，而是页面上真实存在的区域。

后续默认优先按这些区域理解：
- 产品详情
  - 价格横幅/价格信息栏
  - 起售价
  - 价格说明弹层
  - 选择团期入口
- 日历弹窗
  - 套餐区/线路区
  - 月份区
  - 团期卡片
  - 出行人数/份数/房间数/车型数
  - 房差说明/车差说明
  - 已选浮条
  - 底部按钮
- 全部日历弹窗
  - 月份区
  - 日期列表
  - 咨询入口
  - 余位短信通知
- 选择资源页
  - 进度条
  - 已选信息回显
  - 资源 icon
  - 我要咨询入口

## 四、文字规则怎么挂到原型区域

### 1. 展示类规则
- 写的是哪一块显示什么，就挂到那一块区域下。
- 例如：
  - 起售价显示规则 -> `起售价&价格说明弹层`
  - 已减￥XX -> `价格横幅/价格信息栏`
  - 仅余N人/份/车/房间 -> `团期卡片` 或 `出行时间`

### 2. 入口类规则
- 写的是点哪里，就挂到对应入口下。
- 例如：
  - 查看价格说明 -> `价格横幅/价格信息栏` 或 `起售价`
  - 查看全部日期 -> `日历弹窗-团期区`
  - 我要咨询 -> `车差区` / `资源页`

### 3. 弹层类规则
- 写的是弹层里显示什么，就挂到弹层本身，不要留在入口节点里。
- 例如：
  - 常规售价/限时直降/当前起价/起价说明 -> `价格说明弹层`
  - 房费按2人占床... -> `房差说明弹层`

### 4. 跨区域规则
- 若一条规则影响多个区域，要拆开分别挂，不要只挂一处。
- 例如：
  - “点击横幅打开价格说明弹层”
    - 一部分属于 `价格横幅`
    - 一部分属于 `价格说明弹层`

## 五、这类需求里最容易漏掉的组合维度

后续遇到相似需求，优先检查这些维度是否已经拆开：

### 价格维度
- 1成人&1儿童双起价
- 单一起价
- 仅成人起价
- 兜底最低1儿童价
- 兜底最低组合价
- 调价
- 立减团
- 返现团
- 调价+立减
- 调价+返现
- 开售前可看价
- 开售前模糊价

### 团期/场次维度
- 售卖中
- 即将售罄
- 已成团
- 未成团
- 可候补
- 已售罄
- 已满额
- 已截止

### 展示结构维度
- 多线路
- 非多线路
- 预定人数
- 预定份数
- 卡预约

### 数量项维度
- 成人数
- 儿童数
- 多儿童年龄带
- 房间数
- 车型数

### 咨询链路维度
- 配置专属客服
- 未配置专属客服但有咨询群
- 未配置专属客服且无咨询群

### 身份/时间维度
- 未登录
- 已登录
- 设置开售
- 未设置开售
- 距开售/距结束倒计时

## 六、哪些地方默认写成大 case

这次验证下来，下面这些模块更适合写成一个大 case，再在预期里展开多分支：
- 价格横幅
- 起售价&价格说明弹层
- 团期卡片
- 出行人数
- 已选浮条&底部按钮
- 全部日历日期列表

原因：
- 默认态、切换态、异常态高度耦合
- 用户原稿本身就是“大 case + 多分支”
- 拆太碎后更不像用户风格

## 七、哪些地方默认单独拆 case

下面这些地方不要只在大 case 里顺带一句，要单独落 case：
- 房差说明
- 车差说明
- 价格明细
- 余位短信通知
- 咨询专员
- 进群咨询
- 候补添加专员
- 候补进群咨询
- 埋点按钮事件

原因：
- 转化敏感
- 入口独立
- 后续很容易单独回归

## 八、这类需求里的埋点知识点

### 1. 埋点树要单独拆
- 前端展示和神策埋点默认拆成两棵一级树：
  - `+前端`
  - `+神策埋点`

### 2. 埋点标题优先贴按钮语义
- 优先写：
  - `查看价格说明`
  - `计算我的出行价格`
  - `查看全部日期`
  - `房差说明`
  - `车差说明`
  - `价格明细`
  - `更多日期咨询专员`
  - `更多日期进群咨询`
  - `候补添加专员`
  - `候补进群咨询`

### 3. 埋点 case 默认一条 button_name 一个 case
- 不要为了省事把多个按钮合并成一个 case。
- 预期默认直接写：
  - `记神策事件 XXX，button_name：YYY`

## 九、返工时怎么判断自己又写偏了

如果出现下面任一情况，说明又开始偏了：
- 模块名写成 `起价逻辑`、`库存逻辑`、`规则说明`
- 预期里出现 `按规则显示`、`正常展示`、`符合需求`
- 分支句子停在半截，例如“取最低价场次显示该场次价格”，却没写最终页面值
- 用户原稿是一个大 case，你却拆了很多碎 case
- 埋点里多个 button_name 被合并到一个 case

## 十、后续处理同类需求的默认动作

只要遇到“日历改造 / 团期 / 起售价 / 价格说明 / 全部日期 / 选择资源 / 咨询入口 / 埋点”这类需求，默认先做：

1. 打开原型图或 HTML 原型页。
2. 对照 `prototype-alignment-template.md` 做原型落位。
3. 对照用户原稿/XMind 学模块骨架和编号节奏。
4. 对照本文件检查业务组合是否拆全。
5. 最后才写正式 case。
