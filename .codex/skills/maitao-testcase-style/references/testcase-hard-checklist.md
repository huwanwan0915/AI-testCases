# 测试用例硬检查清单

本清单适用于本仓库所有测试用例编写，不只适用于某一个功能。

## 写前先过
- 先按原型/页面真实区域拆模块，不先按抽象逻辑分组。
- 先判断当前内容应收成一个完整 case，还是应拆成多个独立 case；不要强行写大用例。
- 先拆条件维度，再列有业务意义的排列组合，再落用例。

## 编号规则
- 顶层顺序内容用 `1.` `2.` `3.`
- 固定元素/固定展示/固定交互/固定输入用 `1）` `2）` `3）`
- 真正的“条件不同 -> 结果不同”用 `a.` `b.` `c.`
- 分支里的固定补充说明用 `b-1）` `b-2）` `c-3-a）`
- 禁止混写成 `1.a.`、`1-2a.`、`2.d-1.`

## 分支判定
- 看是不是“条件不同 -> 结果不同”，是就拆 `a. b. c.`
- 看是不是固定说明清单，是就写 `1） 2） 3）`
- 若一条里并列了多个条件对象，且每个对象结果分别成立，也按分支处理，不要压成一个顺序句子
- 若一条里写的是“映射关系 / 归类关系 / 对应关系”，只要对象不同且落点不同，也按分支处理，不要压成一个顺序句子

典型要拆分支的写法：
- `团购 / 卡预约 / 隐藏 / 不可售`
- `有数据 / 无数据`
- `单线路 / 多线路`
- `有评价 / 无评价`
- `未完成 / 已完成`
- `当前浏览 / 非当前浏览`
- `H5 / 小程序 / App`
- `国内长途游 / 境外游 / 国内短途游 / 多日营 -> 对应品类`

## 预期书写顺序
- 先写页面元素/固定说明
- 再写交互变化
- 再写条件分支
- 最后写空态/异常态/边界态

## XMind 与 Coding 入库
- 最终若要给 Coding 入库，层级必须是：`用例名称 -> 测试步骤 -> 预期结果`
- 不要插入独立的 `测试步骤` 或 `预期结果` 标签节点
- `预期结果` 必须是叶子节点
- `1）2）3）`、`a. b. c.`、`b-1）` 这类内容都直接写在 `预期结果` 节点正文里
- 不要在 `预期结果` 后继续展开新的 XMind 子节点
- 使用 `scripts/markdown_to_xmind.js` 生成成品时，若目标是 Coding 入库，优先加 `--coding-import`

## 文件落位
- `testcases/` 只保留最终 `.xmind`
- 中间结构稿、返工稿、反导稿默认放 `/tmp` 或系统临时目录

## 交付前自检
- 模块是否按页面从上到下组织
- 是否把卡片元素错误漂成并列模块
- 是否为了追求完整把独立目标硬并成大 case
- 固定描述是否用了 `1）2）3）`
- 分支结果是否用了 `a. b. c.`
- 并列条件对象是否已拆分支
- 最终 `.xmind` 是否仍符合 `用例名称 -> 测试步骤 -> 预期结果`
- `预期结果` 是否仍为叶子节点
